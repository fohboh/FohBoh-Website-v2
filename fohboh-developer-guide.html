Overview

MGE, the Metrics Governance Engine, certifies evidence. You send one location's evidence for one module and one fiscal period; MGE runs a deterministic certification, with no AI anywhere in it, and seals the result as an append-only vault record carrying a Trust Score (0–100), an outcome, certified findings, reconciliations and a cryptographic seal that anyone can verify.

The API has two doors and a public surface. Each key opens exactly one door.

DoorWho uses itEndpoints
Write (Contract №1)Whoever submits evidencePOST /certify · POST /certify/batch · GET /jobs/{id} · GET /modules · GET /modules/{id}/schema
Read (Contract №2)Whoever displays resultsGET /vault · GET /vault/{id} · GET /vault/{id}/evidence · GET /vault/{id}/exportpack · GET /recoveries · GET /rules
Public (no key)AnyoneGET /vault/{id}/verify · GET /keys · GET /openapi.json
Base URL. Production: https://api.fohboh.ai/mge/v1. Your sandbox host and keys arrive with your access sheet during onboarding. The machine-readable reference, OpenAPI 3.1 generated from the same contract package, is always at GET /mge/v1/openapi.json; a dated copy is available to download.
MGE certifies; it does not recover money or give advice. It holds no disputes, letters or tasks. Your product presents MGE's certified facts under your own brand.

Five minutes

Quickstart

  1. Get sandbox keys. Request sandbox access; during onboarding FohBoh issues a write key and a read key (mge_write_sbx_…, mge_read_sbx_…). Every sandbox certification is a TEST RUN: never billed, deletable, and never written to write-once storage.

  -H "Idempotency-Key: loc-0142:M02:doordash:2026-08-01:r1" \

Security

Authentication & keys

Every call except the public ones sends a bearer key:

Authorization: Bearer mge_write_sbx_<your key>

Each key is scoped to integration × location group × door, and to one environment:

ScopeMeaning
IntegrationYour integration id, for example acme-pos.
Location groupA set of your client's locations. A key acts only on locations inside its group.
Doorwrite or read. A write key cannot read vault records; a read key cannot submit evidence. GET /jobs/{id} and GET /modules accept either.
Environmentsandbox (mge_…_sbx_…): every certification is a TEST RUN. production (mge_write_…, mge_read_…): real, billable certifications, issued only after FohBoh's production approval.
  • Shown once. FohBoh shows a key one time when it is issued; MGE keeps only its SHA-256 fingerprint. Store it in your secret manager immediately. FohBoh never sends keys by email.
  • Expiry. Sandbox keys last 30 days and production keys up to a year. Every authenticated response carries an MGE-Key-Expires header, so you can rotate in good time.
  • Rotation. Ask FohBoh for a new key, switch over, then have the old key revoked. Both work during the overlap.
  • No OAuth. MGE uses scoped API keys only; there is no user sign-in on the API.
SituationStatuserror.code
No Authorization header, or an unknown or revoked key401UNAUTHENTICATED
An expired key (rotate before the date in MGE-Key-Expires)401KEY_EXPIRED
The key's door cannot use this endpoint (for example a read key on /certify)401KEY_SCOPE
The location is outside the key's location group401LOCATION_NOT_IN_SCOPE
A record that belongs to another account404NOT_FOUND (MGE never confirms that it exists)

Batch. POST /certify/batch takes { "requests": [ … 1–50 … ] } and returns 202 { "jobs": [ … ] } in request order. A batch is not atomic: MGE stops at the first request it refuses and returns that error; the requests before it were accepted. Put an idempotency_key on every batch request so resending after a fix is safe.

Asynchronous

Jobs & polling

statusMeaning
queuedAccepted and stored; accepted work survives a server restart.
processingBeing certified.
certifiedSealed. vault_id and the full record are present.
failedNot sealed; error.code says why. No vault record exists.

Poll with backoff: start near estimated_ms, then slow down. Webhooks are not available yet.

Job failure codeMeaningWhat to do
PERIOD_NOT_FISCALThe period is not one whole fiscal period (M01: not a 1–35 day statement period).Send the fiscal or statement period.
SCHEMA_VIOLATIONA record failed an intake check the request schema cannot express.Fix the record and resubmit.
NO_STATEMENT · NO_INVOICEThe module's anchor document is missing.Include the statement or invoice.
ORPHAN_LINEA line with no statement or invoice header.Include the header.
DUPLICATE_ORDER · DUPLICATE_STATEMENTAn id appears twice.De-duplicate.
MIXED_PROCESSORM01: records from more than one processor.Certify each processor account separately.
MODULE_NOT_ACTIVEThe module stopped accepting certifications.Contact FohBoh.
DETERMINISM_FAILURE · INTERNAL_ERRORAn MGE-side integrity or processing error, not your data.Retry with the same idempotency key, then contact FohBoh.

Deterministic by design

Request conventions

  • Money is integer cents; rates are integer basis points (2000 = 20.00%). A float in a money field is refused with 400 SCHEMA_VIOLATION; MGE never rounds for you.
  • Quantities and weights are decimal strings, for example "12.5", at most 4 decimal places.
  • Dates are YYYY-MM-DD; timestamps are ISO 8601 with an offset.
  • Document hashes are lowercase 64-hex SHA-256 of the source document you hold.
  • record_id is your own id (1–128 characters), unique in the request; findings, proofs and gaps cite it back to you. Record order does not matter.

Published bands

Outcomes & states

OutcomeTrust ScoreStateMeaning
CERTIFIED85–100S1Fully certified.
VERIFIED70–84S2Certified with discrepancies.
REVIEWED60–69, or any score with a hard-gate overrideS4Certified on bounded scope: the available evidence only.
FAILED0–59S6The evidence cannot support certification; gaps are itemized.
——S5Pending: no sealed record yet.
——S7Superseded by a later certification.
  • The Trust Score measures evidence coverage, not the number of problems. Findings never lower it: a record can be CERTIFIED and carry large findings. Missing mandatory evidence overrides the outcome to REVIEWED; it never deducts points.
  • Every outcome is sealed. A FAILED outcome is a sealed record; a failed job produced no record.
  • Sealed records are never updated or deleted. To correct evidence, submit a new certification for the same location, module, period and direction; the earlier record moves to S7 and names its replacement in superseded_by. TEST RUNs never supersede.

Trust, but verify

Verification

Public check, no key: GET /vault/{vault_id}/verify?sha256_hash=<64 hex> returns valid, superseded_by and signature_valid, and reveals nothing else about the record.

{
  "vault_id": "vr_a2e1f8d6429ae4afb0f912833c8c6827",

Safe retries

Idempotency & retries

  • MGE identifies a submission by its idempotency_key, then the Idempotency-Key header, then the canonical SHA-256 of the request itself, so an identical body resent without a key returns the same job.
  • Same key, same request: 202 with the same job_id and its current status. Nothing is re-run and nothing is billed.
  • Same key, different request: 409 IDEMPOTENCY_CONFLICT.
  • Recommended key: <location_id>:<module_id>:<period.start>:<revision>. Bump the revision when you deliberately re-certify corrected evidence.
  • Retry 429 after Retry-After, and 5xx with backoff and the same key. Never retry a 4xx unchanged.

Stability

Versioning & deprecation

  • The major version is in the path (/mge/v1). Within a major version, changes are additive only: new optional fields, new endpoints, new values. Ignore fields you do not recognize.
  • A breaking change ships as a new major version, announced in advance; the previous major version keeps working for 12 months after the notice, so both versions run side by side.
  • The contract is published as versioned schemas generated from one source; GET /openapi.json always describes the version you are calling. Partners receive the contract changelog during onboarding.
  • Sealed records keep the formula and rule-set versions they were certified under, forever.
